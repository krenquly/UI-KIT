# ATLAS UI Kit — Отчет по практической работе

## 1. О проекте и решенная проблема
Команда веб-разработки создает панель Help Desk. Изначально в коде были несогласованные цвета, отступы и разные стили одинаковых элементов. В рамках данной работы была спроектирована и реализована техническая основа UI Kit.

**Что сделано:**
- Создана 3-уровневая система токенов (примитивы → семантика → компоненты).
- Реализована тёмная тема с поддержкой системных настроек (auto) и ручным приоритетом (light/dark).
- Завершены стили компонентов: кнопки, поля ввода, уведомления (включая состояния hover, active, focus, disabled, invalid).
- Добавлена самостоятельная часть: компактный режим плотности и предупреждающее уведомление (warning).
- Обеспечена адаптивность от 320 px без горизонтального скролла.

**Стек и ограничения:**
Vanilla HTML + CSS (Custom Properties) + Vanilla JS. Без Bootstrap, Tailwind, UI-библиотек, inline-цветов и `!important`.

## 2. Архитектура токенов (3 уровня)

Система построена по принципу **primitive → semantic → component**.

### Уровень 1. Примитивы (`--base-*`)
Значения без привязки к интерфейсной роли.
```css
--base-blue-700: #1853a4;
--base-slate-950: #142338;
--base-white: #fff;

## Схема токенов: Primitive → Semantic → Component

В проекте используется трехуровневая архитектура токенов. Изменение значения 
на первом уровне автоматически (через цепочку `var()`) меняет вид компонента 
на третьем уровне.

### Визуальная схема цепочек


[ПРИМИТИВ]             [СЕМАНТИКА]            [КОМПОНЕНТ]                   [ЭЛЕМЕНТ]
--base-blue-700  ──→  --color-primary    ──→  --button-bg-primary       ──→  .button--primary
--base-slate-950 ──→  --color-text       ──→  --button-text-secondary   ──→  .button--secondary
--base-white     ──→  --color-on-primary ──→  --button-text-primary     ──→  .button--primary (текст)
--base-slate-600 ──→  --color-text-muted ──→  --button-text-disabled    ──→  .button:disabled

Ответы на вопросы
а) Почему плотность задается компонентными токенами?
Плотность — это геометрическое свойство (высота, отступы, интервалы), а не цветовая роль. Переопределение на уровне --button-height, --control-height, --component-gap позволяет изменить вид всех компонентов одним правилом :root[data-density="compact"], без дублирования правил .button/.input и без риска конфликта с цветовой темой.

б) Почему тёмная тема не должна хранить прямые цвета внутри .button?
Компонент должен знать только свою роль (--button-bg-primary), а не конкретный оттенок. При смене темы мы переопределяем семантические токены, и все компоненты подхватывают новые значения автоматически. HEX внутри .button потребовал бы отдельных правил под каждую тему и нарушил бы принцип «изменение в одном месте — результат во всем интерфейсе».
